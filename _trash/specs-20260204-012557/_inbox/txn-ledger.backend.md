# Transaction Ledger + Lot Tracking + Performance (TWR/XIRR) — Backend/Feasibility Notes

Date: 2026-02-04 (UTC)

## Goals

- **Single source of truth** for all portfolio activity via an **append-only-ish transaction ledger** (with controlled corrections).
- Support **accurate cost basis / realized P&L** via **lot tracking** (FIFO by default; optionally specific ID / average cost later).
- Compute **performance**:
  - **TWR** (Time-Weighted Return) for manager skill excluding external cash flows.
  - **XIRR** (money-weighted return) at portfolio and optionally per-asset.
- Scale to:
  - Many users with small-to-moderate transaction volume.
  - “Reasonable” history (10k–200k ledger rows per user) without pathological slowness.

Non-goals (initially): full tax-lot wash sale logic; derivatives/complex corporate actions beyond splits/mergers; intraday performance.

---

## Core Design Principles

1. **Ledger is canonical**: positions, lots, holdings, realized P&L, and performance are derived from ledger events.
2. **Deterministic replay**: given the same ordered transactions and price series, the derived state must be reproducible.
3. **Idempotent writes**: imports and API creates should be safe to retry.
4. **Corrections via versioning**: avoid in-place mutation where it breaks auditability.

## Data Model (Relational / Postgres-friendly)

> Names are suggestions; adapt to existing schema conventions.

### 1) Reference tables

**users**
- `id`

**portfolios**
- `id`, `user_id` (FK), `base_currency` (e.g., USD), `name`, `created_at`

**accounts**
- `id`, `portfolio_id` (FK), `name`, `institution`, `account_type`, `currency`, `created_at`

**assets**
- `id`, `type` (equity/etf/fund/cash/crypto/etc)
- `symbol` (nullable if private), `isin` (nullable)
- `currency`
- `name`
- Unique constraint on `(type, symbol, isin)` as appropriate.

**fx_rates** (if multi-currency)
- `date`, `base_currency`, `quote_currency`, `rate`

**prices**
- `asset_id`, `date` (EOD), `price`, `currency` (should match asset currency)
- Index `(asset_id, date)`

### 2) Transaction ledger

**ledger_transactions**
- `id` (UUID)
- `portfolio_id` (FK)
- `account_id` (FK, nullable for portfolio-level flows)
- `asset_id` (FK, nullable for pure cash txns)
- `type` (enum)
  - `BUY`, `SELL`, `DIVIDEND`, `INTEREST`, `FEE`, `TAX`, `DEPOSIT`, `WITHDRAWAL`,
  - `TRANSFER_IN`, `TRANSFER_OUT`,
  - `SPLIT`, `MERGER`, `SPINOFF` (optional),
  - `ADJUSTMENT` (rare; correction marker).
- `trade_date` (date) — effective date for portfolio impact
- `settle_date` (date, nullable)
- `quantity` (numeric(36,18), nullable for some types)
- `price` (numeric(36,18), nullable)
- `gross_amount` (numeric(36,18)) — in `tx_currency`
- `fees` (numeric(36,18))
- `taxes` (numeric(36,18))
- `net_amount` (numeric(36,18)) — gross - fees - taxes (sign conventions below)
- `tx_currency` (e.g., USD)
- `fx_rate_to_base` (numeric, nullable; filled at ingest time for determinism OR computed on the fly)
- `base_amount` (numeric) — `net_amount * fx_rate_to_base` if known
- `external_cash_flow` (boolean)
  - true for deposit/withdrawal and user-added flows
  - false for internal flows like dividends that are generated by holdings (policy choice)
- `import_source` (e.g., plaid/broker_csv/manual)
- `import_batch_id` (nullable)
- `source_tx_id` (nullable) — idempotency key for imported items
- `status` (posted/pending/canceled)
- `created_at`, `updated_at`
- `superseded_by_id` (nullable FK to ledger_transactions) to support correction/versioning

**Sign convention** (recommendation)
- For asset transactions:
  - BUY: `quantity > 0`, `net_amount < 0` (cash outflow)
  - SELL: `quantity < 0`, `net_amount > 0` (cash inflow)
- For cash flows:
  - DEPOSIT: `net_amount > 0`
  - WITHDRAWAL: `net_amount < 0`

**Constraints / indexes**
- Unique `(portfolio_id, source_tx_id, import_source)` when `source_tx_id` not null.
- Indexes:
  - `(portfolio_id, trade_date, id)` for ordered replay
  - `(portfolio_id, asset_id, trade_date)`
  - `(portfolio_id, account_id, trade_date)`

### 3) Lot tracking

Two feasible approaches:

#### A) Derived lots via “lot events” (recommended)

Store lots as derived records with references back to ledger.

**lots**
- `id` (UUID)
- `portfolio_id`
- `asset_id`
- `account_id` (optional; depends if lots are account-specific)
- `open_tx_id` (FK to ledger_transactions)
- `open_date`
- `open_quantity`
- `open_cost_base` (in base currency)
- `remaining_quantity`
- `status` (open/closed)

**lot_closures**
- `id`
- `portfolio_id`
- `asset_id`
- `sell_tx_id` (FK to ledger_transactions)
- `lot_id` (FK)
- `closed_quantity`
- `proceeds_base`
- `cost_base`
- `realized_pnl_base` (= proceeds - cost)

This model supports FIFO by default but can support specific-lot selection by allowing the sell to specify allocations.

#### B) Fully computed on the fly

No persistence for lots, compute via replay each time. Feasible for small histories but becomes slow for bigger portfolios and repeated queries.

**Recommendation**: Persist derived lots & closures with a robust rebuild path.

### 4) Derived state / snapshots (performance)

**positions_daily**
- `portfolio_id`, `asset_id`, `date`
- `quantity` (end-of-day)
- `market_value_base`
- `cost_basis_base` (optional)
- `unrealized_pnl_base` (optional)

**portfolio_valuation_daily**
- `portfolio_id`, `date`
- `nav_base` (market value of holdings + cash)
- `cash_base`
- `external_flow_base` (net external contributions on that date)

**performance_series** (optional; could be computed at query time from valuation_daily)
- `portfolio_id`, `date`
- `twr_daily_return`
- `twr_cumulative`

## Computations

### 1) Position building (high level)

Inputs:
- Ordered ledger transactions by `(trade_date, id)` for determinism.
- Price series and FX rates.

Process:
- Maintain running quantities per `(portfolio_id, asset_id)`.
- For BUY/SELL, update quantity.
- For DIVIDEND/INTEREST/FEE/TAX: affect cash and realized/unrealized metrics depending on policy.
- For SPLIT: multiply quantity by split factor, adjust lot share counts and per-share cost.

### 2) Lot allocation / realized P&L

For each **BUY**:
- Create lot with `open_quantity=qty`, `open_cost_base = abs(base_amount)` (include fees in cost).

For each **SELL**:
- Determine proceeds in base currency (net of fees/taxes as policy).
- Allocate sold quantity across open lots using FIFO:
  - For each lot, take `min(remaining, abs(sell_qty))`.
  - Cost basis allocated proportionally: `lot.open_cost_base * (qty_taken / lot.open_quantity)` or track remaining cost with remaining qty.
  - Record `lot_closures` rows.

Important edge cases:
- Partial fills (multiple sells on same day): ordering by `id`.
- Short positions: either disallow initially or model negative lots.

### 3) Daily valuation

For each date D (EOD):
- `market_value_base = sum_over_assets(quantity * price(D) * fx_to_base(D)) + cash_base(D)`
- Determine `cash_base` by replaying cash movements:
  - Cash currency might be multiple; convert to base.

If prices missing on D:
- Use last known price (carry-forward) with explicit “stale” marker OR require price.
- Recommendation: carry-forward for valuation but expose “pricing completeness” in API.

### 4) TWR (Time-Weighted Return)

Compute daily returns excluding external cash flows.

Let:
- `NAV_d` = end-of-day total portfolio value (base)
- `CF_d` = net external cash flow during day d (base)
- `NAV_{d-1}` = prior day NAV

Daily return:
- `r_d = (NAV_d - CF_d) / NAV_{d-1} - 1`

Cumulative TWR over period:
- `TWR = Π(1 + r_d) - 1`

Notes:
- Requires consistent timing convention (flows assumed at start-of-day or during-day). Daily formula above treats CF as occurring during day; common simplification.
- For more accuracy, compute sub-period returns within a day if you have timestamps.

### 5) XIRR (Money-Weighted Return)

Compute IRR on irregular cash flows.

Cash flow series for portfolio:
- Contributions (deposits) are **negative** flows from investor perspective? Choose consistent sign.
  - Typical XIRR: money invested is negative, money returned is positive.
- Final value is a terminal cash flow at the end date: `+NAV_end`.

Solve for rate `r` such that:
- `NPV(r) = Σ CF_i / (1 + r)^{(t_i - t_0)/365} = 0`

Algorithm:
- Newton-Raphson with bracketed fallback (bisection) for robustness.
- Guardrails:
  - Require at least one negative and one positive CF.
  - Cap rate search range (e.g., [-0.9999, 10])
  - Handle multiple roots (rare but possible) by choosing economically reasonable root.

Per-asset XIRR:
- Use asset-specific flows (buys/sells/dividends) and terminal value of remaining position.
- Beware that internal transfers (between accounts) should net to zero and be excluded.

## API / Backend Approach

### Write path

**POST /portfolios/:id/transactions**
- Accept single transaction or batch.
- Support `idempotency_key` (or source_tx_id + import_source).
- Validate:
  - currency presence
  - quantity/price/amount consistency
  - allowed types

**POST /portfolios/:id/imports/broker-csv**
- Upload parsing yields staged rows, user confirms mapping.
- Once confirmed, create ledger rows with `import_batch_id`.

**Correction model**

Prefer a “supersede” strategy:
- Original transaction remains immutable.
- New transaction is inserted with corrected fields and `supersedes=<old_id>` or old has `superseded_by_id=<new_id>`.
- All derived tables reference the *effective* transaction in the ordered stream.

### Read path

**GET /portfolios/:id/transactions**
- Filters: date range, asset_id, type, account_id.

**GET /portfolios/:id/lots**
- Open lots, remaining quantity/cost.

**GET /portfolios/:id/performance**
- Params: start/end, frequency (daily/monthly), include_series.
- Returns:
  - twr_total, xirr_total
  - nav_start, nav_end
  - optional daily series.

### Derived state pipeline

Two viable modes:

1) **Synchronous derive on write (simple)**
- After inserting transactions, recompute lots/positions for affected window.
- Good for small datasets.

2) **Async jobs + incremental rebuild (recommended)**
- On transaction write, enqueue job `rebuild_portfolio_from_date(portfolio_id, min_affected_date)`.
- Rebuild positions/lots/valuation from that date onward.
- Keep “last_built_at” and “build_status” in portfolio.

**Feasibility**: Mode (2) is more complex but enables scale and avoids slow writes.

### Incremental rebuild strategy

- Find earliest date impacted by new/changed transaction: `min(trade_date)` among new/superseded.
- Delete derived rows from that date onward for that portfolio in:
  - lots/lot_closures affected asset(s)
  - positions_daily
  - valuation_daily
  - performance_series
- Replay ledger transactions from `min_date` forward to regenerate.

Optimization:
- Maintain occasional **checkpoints** (e.g., monthly position snapshots) to avoid full replay.

## Migration Plan (from existing “simple holdings”)

Assumption: existing system stores current holdings and maybe basic trade history.

### Phase 0 — Prep
- Add new tables (ledger_transactions, lots, derived tables) with migrations.
- Add feature flags for “new ledger” read paths.

### Phase 1 — Backfill ledger
- Convert existing trades into ledger_transactions.
- For users with only holdings (no history):
  - Insert synthetic `ADJUSTMENT` or `BUY` at “as-of date” with estimated cost basis (user-provided or unknown).
  - Mark as `import_source = legacy`.

### Phase 2 — Build derived state
- Run rebuild jobs per portfolio to generate lots and valuations.
- Validate:
  - position quantities match legacy holdings.
  - cash reconciliation where possible.

### Phase 3 — Dual-read
- Serve performance and lots from derived tables; compare with legacy calculations.
- Log discrepancies.

### Phase 4 — Cutover
- Switch UI/API to ledger-backed views.
- Deprecate legacy holdings writes; keep a compatibility layer if needed.

## Risks & Mitigations

### 1) Ambiguous data / broker import inconsistencies
- Risk: missing fees, wrong sign conventions, corporate actions not represented.
- Mitigation:
  - strict validation + staging UI
  - store raw import JSON per row for audit
  - correction workflow (supersede)

### 2) Performance / rebuild cost
- Risk: replay from inception too slow for active users.
- Mitigation:
  - incremental rebuild from min impacted date
  - checkpoints (monthly)
  - derived tables with indexes
  - background jobs + status indicators

### 3) Multi-currency complexity
- Risk: FX timing differences create confusing returns.
- Mitigation:
  - choose deterministic FX policy: store `fx_rate_to_base` per txn at ingest time
  - track base amounts explicitly
  - expose FX rates used in API for transparency

### 4) Corporate actions / splits
- Risk: lots become wrong if splits are mishandled.
- Mitigation:
  - treat splits as ledger events
  - unit tests for split + subsequent sells

### 5) XIRR numeric instability / multiple roots
- Risk: Newton method diverges.
- Mitigation:
  - bracketed solver fallback
  - rate caps and max iterations
  - return “no solution” with explanation when flows invalid

### 6) Auditability vs editability
- Risk: users expect to edit past txns freely.
- Mitigation:
  - supersede model + UI that shows history
  - clear rebuild status & “as-of” computations

## Feasibility Summary

- **Transaction ledger + FIFO lots** is straightforward and robust with a rebuildable derived-state pipeline.
- **Daily TWR** is feasible with valuation_daily + external flow tracking; accuracy depends on price completeness and flow timing granularity.
- **XIRR** is feasible with a robust numeric solver; per-asset XIRR is feasible but needs clear inclusion rules.
